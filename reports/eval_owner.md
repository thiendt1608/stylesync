# Phase 5 eval: owner commit/comment set

40 items the owner wrote by hand (plan section 9): a neutral draft and the owner's own version, split by task. As in `rewrite_style`, only a commit's body is rewritten and compared; the conventional prefix and trailers are kept by code. With n = 40, one item moves a rate by 2.5%. Generated by `stylesync-eval report --set owner`; aggregates only, no message text. Good/bad examples stay in `data/eval/owner/` (private).

## Systems

- `neutral`: the input unchanged (floor). `reference`: the owner's own version (ceiling).
- `base-*`: Baseline A, base model zero-shot with the descriptive MCP prompt, greedy.
- `ft-*`: base model + LoRA adapter from Phase 4, training prompt, greedy.
- `fewshot-gpt6luna`: Baseline B, gpt-6-luna with the 10 most similar train pairs (char n-gram TF-IDF, one per burst) as examples.
- Every configured system has outputs.

## Results

- `style`: share classified as the owner's (char n-gram TF-IDF + logistic regression, train outputs vs train inputs). `style_<variant>`: same, split by the neutral input's variant (here the task; the classifier only saw chat, so read it as a rough signal).
- `mean_len` … `codemix`: stylometry as in `reports/data.md` (word shares; emoticon is a share of messages).
- `hard_tokens`: the text of backtick spans and identifiers copied verbatim, over the `hard_token_n` inputs that have one (few in chat; the owner's commit/comment set is where this matters); `placeholder`: same placeholders; `guard`: MCP guard passes (it also needs each span's backticks).
- `meaning` … `low`: gpt-6-luna judge, mean score 1–5, share with added / lost information, share scored ≤ 2. The judge is the same model as Baseline B, so it may favour B: read B's meaning score as an upper bound.
